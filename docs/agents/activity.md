# Activity

Moved out of `AGENTS.md`: read it when working on this area.

The Activity window (`form/activity/`: `ActivityWindow`, `ActivityController`, `WindowActivity`, dockable, password-protected, docked into the Main window by default: `IniUser::mainWindowDocks()`'s default list and `windowDocked()`'s default for `activityWindowGroup()`; opened by the tray's Statistics menu, `HotKey::activity` and `-c window show activity`) shows the live allowed flows by their Programs and processes: a tree of the Programs with flows, their processes (PID, the parent) and the processes' flows (protocol, direction, local address (hidden by default: the header's context menu, `ControlUtil::showHeaderMenu()`) and port, remote address and host name, download/upload speeds, bytes, the start time). Live data only, no history; blocked connections and the traffic decided by the conf's flags alone (no flow context) aren't shown.

## Data

The master's `ActivityManager` (`activity/`) writes the live data into its own SQLite DB (`FortSettings::activityFilePath()`, recreated on the service's start; tables `proc` and `flow`, `activity/migrations/1.sql`) from the log entries `LogManager` gives it: CONN (a flow with `flowLogging()` that isn't blocked, `FORT_LOG_CONN_FLOW_LOGGING`; it adds the flow and its process's row: the Program by the CONN's `app_id`, the parent's path by `StatManager`'s logged processes, if the parent has logged connections and is created earlier; each new flow's CONN replaces its process's row: the Program, the parent; a CONN logged again (after a blocked reauthorization, the master's restart: a reauthorization doesn't log it by `FORT_FLOW_CONN_LOGGED`) keeps the flow and updates its process's Program. So the flows of a process whose Program is added stay under its path till the process's next new flow), PROC_NEW (updates the path of a known process: a CONN logged with the paths before it, the name changed; the path as converted by `StatManager`), FLOW_TRAF (the flows' bytes since the driver's previous tick, 500 ms), FLOW_CLOSED, STAT_TRAF (a process reported inactive has no flows: its flows left are closed). One write transaction per log buffer (a failed commit is rolled back: the changes are lost, the next buffer begins anew), committed at its end (`LogManager::processLogBuffer()` → `ActivityManager::commitChanges()`), `activityChanged()` after the commit; a host name resolved after the flow's CONN (`updateConnHost()`, out of a buffer's processing) is committed at once; only a flow logged without the name waits for it, 5 s (`m_hostWaits`, as `StatConnManager`'s: most names are resolved before the connection, so the other answers write nothing). The speeds are bytes per second: the tick's bytes by the driver's constant log period (`FORT_LOG_TIMER_PERIOD`); a TIME entry zeroes the speeds of the flows without bytes in the previous tick (a tick's FLOW_TRAF entries may span several buffers); the second TIME after the last bytes (`m_trafTick`) clears them all, so the next TIMEs open no transaction. A client's `ActivityManagerRpc` opens the same file read-only; its only RPC is `Rpc_ActivityManager_changed`, which emits `activityChanged()`.

## Model

`ActivityTreeModel` (`model/`, a `QAbstractItemModel`) is owned by the window and reads the DB only while the window is shown (`showEvent()`/`hideEvent()` → `setActive()`; a docked window in a hidden tab is hidden too). On `activityChanged()` it reads both tables in one read transaction and synchronizes its rows by `flow_id` and `pid` by `beginInsertRows()`/`beginRemoveRows()`/`beginMoveRows()`/`dataChanged()`, so the expanded state and the selection are kept; a read into the empty model resets it. Both tables are read in one read transaction: a client reads while the master commits.

- Three levels: the Programs (`ActivityAppNode`, by `proc.app_id`: the name and icon from the conf, reloaded on `ConfAppManager::appsChanged`/`appUpdated`; a process without a Program, `app_id` NULL, is grouped by its path, shown by the path's name; a deleted Program is shown by its first process's path), their processes (`ActivityProcNode`: the exe's name, PID and the Parent column, "name (PID)" or the PID alone when the parent's path is unknown) and the processes' flows. A process whose Program is changed (by its CONN, see above) is moved to the new one (`moveNode()`).
- Only the Programs and processes with flows are shown. A Program's and a process's speeds, bytes and flow count are the sums of their flows.
- A closed flow is removed at once. The rows are sorted only on the header's click (`sort()`); a new row is inserted by the current sort's order, the changed values don't move rows.
- A flow's v4 addresses are `qint32` columns, v6 BLOBs (`SqliteStmt::columnBlob()`).
- Known: a flow whose FLOW_CLOSED is lost (the log's overflow) stays shown, without speeds, till its process is reported inactive by STAT_TRAF.
