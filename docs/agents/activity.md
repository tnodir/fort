# Activity

Moved out of `AGENTS.md`: read it when working on this area.

The Activity window (`form/activity/`: `ActivityWindow`, `ActivityController`, `WindowActivity`, dockable, password-protected, docked into the Main window by default: `IniUser::mainWindowDocks()`'s default list and `windowDocked()`'s default for `activityWindowGroup()`; opened by the tray's Statistics menu, `HotKey::activity` and `-c window show activity`) shows the live allowed flows by their Programs and processes: a tree of the Programs with flows, their processes (PID, the parent) and the processes' flows (direction, protocol, local address and port, remote address and port, host name, the reason (`ConnListModel::reasonText()`: "Unknown" for the Filter Disabled with the traffic collected; the direction and the reason are shown by their icons only, as in the Connections: the header's icons of `ConnListModel::columnIconPath()`, fixed width, the texts in the tooltips; sorted by the reason's text), download/upload speeds, bytes, the start time). The tree's column names a process "Process <PID>" (its own exe of the Program; else, a wildcard Program's process, by the exe's name and PID) and a flow by the remote host's name or address and port (and the protocol in parentheses, if not TCP; the direction by its icon), so the PID, protocol, local, remote address and port, host name and direction columns are hidden by default, the reason's too (the header's context menu, `ControlUtil::showHeaderMenu()`). Live data only, no history; blocked connections and the traffic decided by the conf's flags alone (no flow context) aren't shown.

## Data

The master's `ActivityManager` (`activity/`) writes the live data into its own SQLite DB (`FortSettings::activityFilePath()`, recreated on the service's start; tables `proc` and `flow`, `activity/migrations/1.sql`) from the log entries `LogManager` gives it: CONN (a flow with `flowLogging()` that isn't blocked, `FORT_LOG_CONN_FLOW_LOGGING`; it adds the flow with its reason and the reason's details (the Rule, the Zone, the Terminating Rule, loopback, the inherited Program's path), with `local_net` by `FORT_LOG_CONN_LOCAL_NET`: the driver's `is_local_net` by the LAN addresses, computed with the Filter Disabled too while the traffic is collected; not shown yet, and its process's row: the Program by the CONN's `app_id`, the parent's path by `StatManager`'s logged processes, if the parent has logged connections and is created earlier; each new flow's CONN replaces its process's row: the Program, the parent; a CONN logged again (after a blocked reauthorization, the master's restart: a reauthorization doesn't log it by `FORT_FLOW_CONN_LOGGED`) keeps the flow and updates its reason with the details and its process's Program. So the flows of a process whose Program is added stay under its path till the process's next new flow), PROC_NEW (updates the path of a known process: a CONN logged with the paths before it, the name changed; the path as converted by `StatManager`), FLOW_TRAF (the flows' bytes since the driver's previous tick, 500 ms), FLOW_CLOSED, STAT_TRAF (a process reported inactive has no flows: its flows left are closed). One write transaction per log buffer (a failed commit is rolled back: the changes are lost, the next buffer begins anew), committed at its end (`LogManager::processLogBuffer()` → `ActivityManager::commitChanges()`), `activityChanged()` after the commit; a host name resolved after the flow's CONN (`updateConnHost()`, out of a buffer's processing) is committed at once; only a flow logged without the name waits for it, 5 s (`m_hostWaits`, as `StatConnManager`'s: most names are resolved before the connection, so the other answers write nothing). The speeds are bytes per second: the tick's bytes by the driver's constant log period (`FORT_LOG_TIMER_PERIOD`); the tick's last FLOW_TRAF portion (`LogEntryFlowTraf::isTickEnd()`: shorter than `FORT_LOG_FLOW_TRAF_BUFFER_FLOW_COUNT`, the driver writes an empty one if needed; a tick's portions may span several buffers) zeroes the speeds of the flows without bytes in the tick; only the previous tick's speeds may stay (`m_hasSpeeds`), so an idle tick after the cleared ones opens no transaction. A portion lost by the buffer's error delays the zeroing to the next tick's end. A client's `ActivityManagerRpc` opens the same file read-only; its only RPC is `Rpc_ActivityManager_changed`, which emits `activityChanged()`.

## Model

`ActivityTreeModel` (`model/`, a `QAbstractItemModel`) is owned by the window and reads the DB only while the window is shown (`showEvent()`/`hideEvent()` → `setActive()`; a docked window in a hidden tab is hidden too). On `activityChanged()` it reads both tables in one read transaction and synchronizes its rows by `flow_id` and `pid` (WFP's `flowHandle` isn't documented as unique, though on Windows 11 it counts the flows since the boot: 7013 short TCP/UDP flows on the VM got consecutive ids, none reused) by `beginInsertRows()`/`beginRemoveRows()`/`beginMoveRows()`/`dataChanged()`, so the expanded state and the selection are kept; a read into the empty model resets it. Both tables are read in one read transaction: a client reads while the master commits.

- Three levels: the Programs (`ActivityAppNode`, by `proc.app_id`: the name (in bold) and icon from the conf, reloaded on `ConfAppManager::appsChanged`/`appUpdated`; a process without a Program, `app_id` NULL, is grouped by its path, shown by the path's name; a deleted Program is shown by its first process's path), their processes (`ActivityProcNode`: "Process <PID>" when its path is the Program's (`isAppExeProc()`: the normalized path of a non-wildcard Program, the key's path of an unknown one), else "name (PID)"; the icon of the exe; the full path in the Program column's tooltip; the Parent column, "name (PID)" or the PID alone when the parent's path is unknown; the parent's path in its tooltip) and the processes' flows. A process whose Program is changed (by its CONN, see above) is moved to the new one (`moveNode()`).
- Only the Programs and processes with flows are shown. A Program's and a process's speeds, bytes and flow count are the sums of their flows.
- A closed flow is removed at once. The rows are sorted only on the header's click (`sort()`); a new row is inserted by the current sort's order, the changed values don't move rows.
- A flow's row is a `Conn` (`ActivityFlowRow`): the Reason column's tooltip is `ConnListModel::reasonDetailsText()`, with the process's path as the flow's `appPath` (an inherited Program of the process's own path is shown as "Inherited").
- A flow's v4 addresses are `qint32` columns, v6 BLOBs (`SqliteStmt::columnBlob()`).
- Known: a flow whose FLOW_CLOSED is lost (the log's overflow) stays shown, without speeds, till its process is reported inactive by STAT_TRAF.
