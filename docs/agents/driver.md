# Kernel driver: event log, traffic accounting, WFP provider

Moved out of `AGENTS.md`: read it when working on this area.

## Event log

The driver writes its errors to the System event log by `TRACE(event_code, status, error_value, sequence)` (`forttrace.c`; the Config info events only with the "Trace Driver Events" option). The event codes are defined in `driver/evt/fortevt.mc` (a facility's MessageIds start at its number × 10): after a change regenerate `fortevt.h` and `FORTEVT_MSG00001.bin` by `mc -z FORTEVT fortevt.mc` in `driver/evt/` (`mcbuild.bat`) and convert the header's CRLF to LF. `driver/common/` is compiled into the UI too, so `TRACE` there is guarded by `FORT_DRIVER` (cf. `fortprov.c`). A user's events: `wevtutil qe System "/q:*[System[Provider[@Name='fortfw']]]" /f:xml /rd:true /c:50`; in an event's `<Binary>` (the `IO_ERROR_LOG_PACKET` header, little-endian) the 4th DWORD is the event code, the 5th `error_value`, the 6th `status` (e.g. `0D0000C0` = `STATUS_INVALID_PARAMETER`).

## Traffic accounting and the WFP provider

The driver's `conf_flags.log_stat` is always set (`ConfData::writeConfFlags()`; the "Collect Traffic Statistics" option is the UI's): while a master is connected, every allowed connection's flow gets its context (`fort_flow_associate()` by the App's check, below; only an allocation or association error skips it, and the conf's flags deciding the connection alone, e.g. the allowed Local Network) and the log timer writes the TIME records. The traffic is counted by the transport callouts (`fortcout_pkt.c`) in Fort's sublayer (the max weight, so before the other drivers' callouts): a packet re-injected by another driver (`FWPS_PACKET_INJECTED_BY_OTHER`, e.g. by NetLimiter's shaper) is skipped as its original packet is counted (unless the "Collect Traffic re-injected by other drivers" option, `log_stat_reinjected`, is set: e.g. the inbound packets diverted by WinDivert at the IP packet layer don't reach the transport layer), a packet blocked by a higher sublayer (BLOCK without the write right) too. 3.20.0–3.20.2 counted it in `FWPM_SUBLAYER_INSPECTION` (the lowest weight, after the other callouts), which would miss the traffic of a driver absorbing the packets and re-injecting them elsewhere: their filters are only deleted now. A failed step aborts the whole reauth transaction (e.g. the flow filters aren't added, so no traffic is counted at all); the reauth compares the conf with the registered provider's state, kept in the device's flags (`FORT_DEVICE_PROV_MASK`: its objects, their boot conf and the flow filters, set after a successful reauth), so the next reauth retries the failed changes; the `FORT_PROV_ADD_ERROR` event names the object failed to add (a filter, callout, sublayer or the provider) by its key's first part. Windows Insider builds (29639, 29680) fail to add a callout deleted in the same transaction (`STATUS_INVALID_PARAMETER`, #768: the provider's recreation on `SETCONF` to enable the boot filter after a reboot failed), so `fort_prov_reregister()` commits the deletions before registering the provider's objects again (on the driver's load and on the boot filter's, stealth mode's or filter locals' change: they're kept in the provider's data, applied on the driver's load before the first conf, which the provider's re-registration only can change). The WFP sublayers' weights seem to be made unique by BFE (a requested weight 0 became 10: 0…8 are built-in, a third-party one took 9); only `FWP_ACTION_CALLOUT_INSPECTION` filters without `FWPM_FILTER_FLAG_PERMIT_IF_CALLOUT_UNREGISTERED` are allowed in `FWPM_SUBLAYER_INSPECTION` (else `STATUS_FWP_INVALID_FLAGS`).
