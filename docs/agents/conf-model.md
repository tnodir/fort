# Configuration model details

Moved out of `AGENTS.md`: read it when working on this area.

## IP Addresses

The "IP Addresses" tab's lists are the two `AddressGroup`s (`FirewallConf::addressGroups()`: include/exclude texts and zones, the Include/Exclude All flags; the driver gets them as `FORT_CONF_ADDR_GROUP`s, checked by `fort_conf_conn_filter_flags_filtered()`). The first one (`lanAddressGroup()`)'s exclude list is the "Local Network Addresses" (a remote address not included by it is LAN: `conn->is_local_net`); the second one (`inetAddressGroup()`)'s exclude list is the Internet's "Block Addresses" (reason `FORT_CONN_REASON_IP_BLOCK_INET`) and its include list the "Allow Addresses" (allowed for any program, after the blocked ones: `FORT_CONN_REASON_IP_ALLOW_INET`; as with the Filter Disabled, `fort_conf_conn_flags_filtered()` returns FALSE for it, so the App's check collects its traffic and logs a new App). The UI doesn't show their Include/Exclude All flags: the DB migration to v68 set the second one's Include All and cleared its old hidden "Include" list; the other flags stay as the old UI set them (e.g. the first one's Include All may be unset). `AddressesPage` shows each list by an `AddressesArea` (`form/opt/pages/addresses/`) of its `FirewallConf::AddressList` (the groups' include and exclude lists in turn: `FirewallConf::addressListZones()`/`addressListText()`, also naming the list in a parse error).

## A Program's Network Filters and Rules

A Program's Network Filters are rule text lines in `app.filters_text` (one filter per line), edited by `FilterEditDialog` (`form/rule/`; the Edit Rule dialog uses it too, to append a line to the Rule's text). Its fields build the read-only line by `FilterLineText` (`util/conf/filterlinetext.h`: named sections, e.g. `IP(1.1.1.1):Port(80):Act(Block)`; also by a connection's `Conn`, for the Connections windows' "Add Filter" and "Copy as Filter"; the common window's "Add Filter" opens the Program's form on the Network Filters tab, a blocked Program's on the General tab till the filter is saved), the dialog gets one; `FilterLine` (`util/conf/filterline.h`) holds it and parses it by its `RuleTextParser`, giving the `RuleFilter`s by type to fill the fields. The Program's Terminating Rule (on the form's Rules tab: `TerminatingRuleSelector`, as in the Edit Rule dialog; Allow, Block or Drop, with an alert) is the last line, after the `# Terminating` comment line, e.g. `Act(Block):Opt(Alert)` (`ConfUtil::parseAppFiltersText()` / `appFiltersText()` give the text's `Rule`: the filters' lines and the Terminating flags; the Network Filters and Rules tabs' pages each replace their part of the text). The Program's Rules (App and Preset Rules) are `app.ruleSet`, the conf DB's `app_rule` rows by `order_index` (read by `group_concat()`, `ConfUtil::parseRuleSetIds()`; a deleted Rule's rows are deleted), edited on the form's Rules tab (`ProgRulesPage`) by the `RuleSetArea` of the Edit Rule dialog's Presets tab; the DB migration to v71 moved the old single `app.rule_id` there. The driver gets them as a `FORT_CONF_RULE` (without zones and Time Period; its set is the Program's Rules) after the path in the app entry (`app_entry.rule_size`, so ADDAPP updates them) and checks the filters, then the Rules, then the Terminating Rule (reason `FORT_CONN_REASON_PROGRAM_FILTER`, or `FORT_CONN_REASON_RULE` with the id of the set's Rule which decided); the rule is checked without the conf's lock (`conn->app.rule`), so an exe entry with a rule is never changed in place nor freed before the conf (`fort_conf_ref_exe_free_entry()`), and its set under the Rules' lock (`fort_devconf_app_rule_conn_filtered()`: a rule without a set doesn't lock).

The driver doesn't check the filters and Rules of a Program with the Block or Kill Process action, and its form's Network Filters and Rules tabs are disabled. A filter saved for it from the Connections windows' "Add Filter" (`ProgMainPage::onFilterSaved()`) switches the form to Allow with the blocking Terminating Rule. The Program's other settings stay and are checked before the filters (`fort_conf_conn_app_filtered()`): its Groups' Rules and Zones may allow more than the filters; they, Block In/Out, LAN Only and a disabled Group may block a filter's address.

## Time Periods

Groups, Speed Limits and Rules may refer to a `TimePeriod` (`conf/timeperiod.h`, max 64: a list of intervals, each with its week days and time from/to) by `period_id`, applied while their `period_enabled` is set. `ConfTimePeriodManager` tracks the Time Periods' activity by minutes. For the Groups and Speed Limits it is folded into their enabled masks written to the driver (`writeGroupFlags()` / `writeSpeedLimitFlags()`). The Rules are checked by the driver: a rule's `period_id` (0 - always active) against the active Time Periods' mask, sent in `FORT_CONF_IO.periods` with `SETCONF` and updated by `SETPERIODS` on the activity's change.

## Hosts Zones

A Zone of the Hosts type (`host` in `conf/zone/types.json`, the `host_text` and `host_file` sources) lists host names, parsed by `HostRange` (`util/net/`): `example.com` matches the name itself only, `*.example.com` its subdomains of any depth but not itself, `.example.com` both (kept as the two names); a name with other masks is matched by `HostPattern` (`ads*.example.com`, `google.*`, `*telemetry*`: `*` is any characters of a label, the leading and trailing ones also any labels before and after it; each of them is checked for every name, so a list has at most `HostRange::patternNamesMax` of them); the names are compared case-insensitively, without the root's trailing dot, an internationalized name is converted to Punycode (`QUrl::toAce()`). `TaskZoneDownloader` keeps the normalized names in the Zone's cache file and gives the driver an empty address list, so the Zone is in the driver's `FORT_CONF_ZONES.mask` and `enabled_mask` like the others. Its addresses are added at runtime by `ADDHOSTIPS` (`FORT_CONF_HOST_IPS`: the IPs of a DNS answer with its TTL, to be sent by the service's DNS forwarder): the driver keeps them in `FORT_HOST_IPS` (`fortcnf_host.c`, max 65535 IPs, the expired ones removed when it's full, at most once a minute: the purge walks all IPs under the lock; an IP has one expiration time for all its Zones). An expired IP isn't matched by a new connection, but is matched by an established connection's reauthorization (`conn->is_reauth`, on any conf's change) for a day more (`FORT_HOST_IP_REAUTH_TIME`), as the connections outlive the TTL; it's removed only then. An expired IP added again keeps its old Zones, for the new connections too, till it expires for the reauthorization (as the IP's Zones share its expiration time anyway). The ALE callout looks up the remote IP's Zones once into `conn->host_zones_mask`, which `fort_conf_zones_ip_included()` checks before the Zones' address lists (the Filter Simulator has no such IPs). `SETZONES` removes the IPs' Zones not in its mask, as a removed Zone's id can be reused; the client's disconnect doesn't clear the IPs: they stay till their TTL, as the DNS clients' caches keep them.
